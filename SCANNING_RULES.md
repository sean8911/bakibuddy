# Image scan rules

## Supported inputs

Phase 6 supports one user-selected JPEG/PNG of printed Latin text at a time: conventional MYR receipts/payment details or the supplied TNG Activity-list layout. Select the matching layout. These are candidates for human review, not verified payment evidence. QR codes never establish payment. Handwriting, non-Latin recognition, scanned PDFs, camera capture, rotated/complex receipts and arbitrary banks/apps are outside the verified scope. Use the Phase 5 PDF importer for the original TNG statement.

Limits: 10 MB, 12,000,000 decoded pixels, 500 recognized lines, 50,000 recognized characters, 50 candidate rows, one worker and 120 seconds per read. The worker checks decoded dimensions independently of picker metadata and resizes the long side to at most 2,400 pixels, upscaling smaller images by no more than 2×. Oversized input requires cropping in Photos. No automatic destructive crop or image overwrite occurs.

## Local reader

Expo ImagePicker 58.0.10 selects an image; no camera/microphone permission is requested. Bundled Tesseract.js 7.0.0, its 7.0.0 portable LSTM WebAssembly core and the English 4.0.0_best_int model run in a WebView, not in Hermes. Supplemental web tests use a sandboxed iframe. No custom native OCR module, external OCR API, CDN model download, AI or backend is used.

`pnpm build:ocr` generates the self-contained 9.35 MB HTML asset and license notice. The worker concatenates unmodified portable core and worker code; the language is a local data URL with the appended filename confined to its fragment. Explicitly choosing the portable core trades SIMD speed for bounded size and compatibility without fetching alternate cores. The asset is loaded separately through Expo Asset so it does not enlarge the JS entry bundle by 9 MB. A development session needs Metro to supply uncached code/assets; cached model execution and local financial storage do not require a network.

CSP allows inline bundled scripts, WebAssembly, one blob worker, data/blob images and data-only model reads; HTTP(S) connections are prohibited. The native document has a reserved `.invalid` base URL solely for WebView origin behavior, with navigation restricted to it/about:blank; it is not a contacted service. Errors, cancellation and timeout remove the reader. A backgrounded scan discards its transient image/text/review. No cloud consent flow exists because no cloud processing is implemented.

Phase 8 traces reproduced a startup stall at `Image.decode()` in the hidden browser reader after sixteen successful reads. The reader now installs image load/error handlers before assigning its source, checks dimensions before canvas/worker setup and retains the original overall 120-second limit. It reports bounded startup phases without recognized text. Terminal result/error messages follow worker termination and object-URL/canvas cleanup so result-driven unmount cannot interrupt that cleanup. A parent load request can repeat the ready handshake; one job still starts only once. Six lifecycle tests exercise delayed termination, failure, duplicate starts, trusted readiness, corrupt-image loading and oversized dimensions. These isolated lifecycle tests do not replace real OCR or native device checks.

## Candidate extraction

TNG Activity uses dated row anchors and geometric grouping. Merchant/amount/type lines belong to each anchor; points and navigation controls never become transactions. A year can come only from a uniquely containing displayed start/end period, with explicit review guidance. Missing/ambiguous years remain blank. Two-digit period years use 2000–2099; unsupported historical centuries need manual correction. Wrapped merchant lines are retained. A negative payment can suggest expense; reloads/wallet transfers/incoming money require classification.

Single-receipt/detail mode prefers one consistent full-payment total. Subtotals, item prices, discounts, tax, tendered cash, change, points and balances are excluded from total selection. Several differing totals or multiple unlabeled currency amounts leave the amount blank. A clearly dated transaction can still need manual amount entry. Full numeric dates use day/month/year in Malaysian format; ambiguous two-digit years stay blank. Printed Latin text and MYR are the initial language/currency scope.

Money parsing requires exact decimal digits/two decimal places. OCR letters are never silently replaced by plausible digits. Amount lines below 50 recognition confidence stay blank; any line below 80 creates an uncertainty warning. These are engine heuristics, not calibrated correctness probabilities. Every included record requires human review regardless of confidence. Raw recognized text and source image remain available during correction, then are discarded; neither is saved to SQLite.

## Review and saving

All candidates start excluded/unreviewed. The selected account is fixed while rows are under review. Each included row needs a valid name, amount, full date, category/type and explicit field-check confirmation. Edits clear that confirmation and any separate-payment acknowledgement. New income, expenses and refunds remain distinct. Transfers require a direction and a different tracked account; the original selected account is the image's account. Sending money to another person may be an expense, while moving your own money is a transfer.

Confirmation lists every selected name/date/type/amount/account and separate expense/income/refund/transfer totals using the shared integer-sen/BigInt utility. No aggregate from OCR becomes authoritative. Only Confirm scanned transactions writes to the ledger. Cancelling any earlier step saves nothing. Save failure preserves the reviewed batch for correction/retry. Imported/scanned scheduled payments must be explicitly linked under Bills & income to replace their reserved forecast amount.

Schema 4 adds `scan_receipts(source_key, transaction_id)`, with unique keys, unique transaction linkage and a cascading foreign key. Source identity is SHA-256 of the processed picker image's base64 bytes plus candidate index and a format version, independent of subsequent user edits or account changes. Only the final source key and transaction ID persist. Editing a record preserves its source lock; explicit deletion removes it and permits re-scanning. Different encodings/crops can produce different source hashes, so source identity is supplemented by a possible-duplicate warning.

Possible duplicates share the same date, exact amount and at least one tracked account, even if OCR changed the name/type or a transfer was entered from its other side. This deliberately broad warning also covers PDF/manual entries and overlapping images; an actual separate payment needs acknowledgement. Differently dated/amount-corrected records can evade this heuristic, so review history when unsure. Strong same-image locks cannot be overridden. Different layouts/engine revisions may group the same image differently; use the original verified layout and inspect locks rather than assuming cropped/reprocessed images are new history.

The serialized repository revalidates reviewed status, dates/amounts, account existence, source keys, IDs and possible duplicates inside one SQLite transaction. Any invalid row, duplicate key, SQL failure, balance/budget overflow or interrupted migration rolls back all new records/receipts. Concurrent confirmations commit the source once. Existing accounts, transactions, TNG wallet identities/receipts, budgets and payment links are preserved by the schema 3→4 migration.

Native ImagePicker-owned cache copies are removed only inside its known cache directory; original Photos images are untouched. Browser-owned blob URLs are revoked. JavaScript/WebView memory is garbage collected; this is not a cryptographic erasure or at-rest encryption guarantee. Physical Android/iPhone WebView/WASM, picker permissions, memory, backgrounding, gestures, safe areas, larger text and assistive technology remain device checks.
