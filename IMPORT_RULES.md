# TNG statement import rules

## Supported source

The user-authorized, text-based landscape PDF layout verified on 27 October 2026: TNG WALLET TRANSACTION HISTORY, wallet identifier and English statement period, then eight columns — Date, Status, Transaction Type, Reference, Description, Details, Amount (RM), Wallet Balance. The original sample has internal page rotation; extraction converts each original PDF text run to viewport coordinates. References and type labels may wrap. Continuation pages need not repeat headers. PDF.js text-content merging combines adjacent columns in this export, so the bounded operator-run extractor preserves the original runs instead.

The separate GO+ TRANSACTION appendix is counted and excluded. Its entries can mirror eWallet movements; importing both would duplicate them. Main-table Success rows are candidates; explicit Failed/Cancelled/Canceled/Pending rows are counted and excluded. Unknown statuses or malformed required cells reject the whole preview. Image-only PDFs, screenshots, physical-card statements, CSVs, other layouts, signed amounts and format variants remain unsupported until separately verified. File limits: 5 MB, 100 pages, 2,000 wallet candidates, 100,000 text segments and 2,000,000 characters, plus a 90-second extraction timeout.

## Exact values and classification

Names use Unicode NFKC, collapsed whitespace and trimming. Dates use actual calendar validation and Kuala Lumpur date-only strings, must be inside the supplied period and no later than today. Money comes only from Amount (RM), with exactly two decimal places and validated comma grouping, converted to integer sen using BigInt. Wallet Balance is separately parsed for source validation; it never becomes a transaction amount or replaces an account's opening balance. Editable amounts still use the ordinary ledger's exact validation and safe integer limits.

Verified QR/Payment labels suggest expense. Receive from Wallet, Reload and DUITNOW_RECEIVEFROM establish money-in direction but require classification as new income, refund or a transfer from another tracked account. Transfer to Wallet and eWallet Cash Out establish money-out direction but require classification as expense or transfer to another tracked account. Unknown source labels require both direction and type. The user decides account ownership. A bank reload is not automatically income; another person's wallet is not automatically the user's own tracked account. An untracked own account must be added first or its row excluded. Internal transfers affect both balances and never income or spending.

No row starts selected. Select suggested payments includes eligible expense suggestions and skips current possible duplicates. Categories start as Other, explicitly disclosed in the preview. Users may edit name, date, amount, category and classification, select/exclude rows, and review ten rows per page. Only selected valid rows reach confirmation; unresolved selected rows block it. Confirmation separately totals expenses, income, refunds and transfer amounts with BigInt/range checks. Only Confirm import writes records.

## Identity and duplicates

The account is an existing tracked eWallet. SHA-256 wallet identity links one source wallet to one account and one account to one wallet. SHA-256 source identity includes a format version, wallet identifier, normalized original source type and complete reference, independently of user edits. A separate fingerprint covers original date, amount, type, merchant and reference. Raw wallet IDs, source PDFs, plaintext passwords and raw source references are not persisted. Hashes provide stable identifiers, not encryption of the ledger or proof that a statement is authentic.

Already-imported source keys are locked, including overlapping date ranges or previously edited records. A same-key different fingerprint is locked as a conflict. Repeated keys in one file are excluded. A weaker possible-duplicate check uses date, kind, amount and both account IDs; expenses/income/refunds additionally compare NFKC/case/whitespace-normalized name. Category is deliberately excluded. Transfer names are ignored so a transfer already entered from its other side is still caught. A legitimate separate transaction can be acknowledged explicitly. This heuristic cannot identify every renamed or differently dated manual record; users must review their history. Strong source-key duplicates cannot be overridden.

Schema 3 adds import_wallets and import_receipts with uniqueness/FK constraints. Repository checks source/account/direction/duplicate rules again inside the serial write transaction, inserts all ledger rows and receipts, validates balances and budget range, and commits them together. Any failure rolls back wallet mapping, receipts and ledger rows. Double submissions commit once. Editing a saved transaction retains source identity; explicitly deleting it cascades its receipt and permits deliberate reimport. An empty account's mapping cascades when that account is deleted. Linked source accounts retain eWallet type.

## Local processing and recovery

Expo DocumentPicker selects the PDF. Native cache-copy size is checked before reading; only the picker-owned copy is removed afterward, never the original. PDF.js 6.4.299 is bundled locally into an isolated native WebView or sandboxed web iframe; CSP disallows network and workers, XFA/font rendering are disabled, and the provider's PDF actions are never executed. The shared runtime is generated with esbuild via pnpm build:pdf; its Apache license is included. No remote converter, login automation, TNG API, cloud AI or backend is used.

Password input is obscured, never persisted, and cleared when reading begins/results arrive, an error occurs, reading is cancelled or the app backgrounds. The reader runtime is removed after extraction/error/cancellation. File bytes are discarded once preview is prepared or reading is cancelled; wrong-password recovery retains the selected file temporarily so only the document password needs re-entry. Leaving the screen discards its preview. Backgrounding interrupts active reading and asks the user to choose again. JavaScript memory is garbage collected; this is not a guarantee of cryptographic memory erasure.

Save failures retain reviewed rows and support retry. Selection/read/preview/cancellation creates no ledger records. Imported records do not automatically settle planned bills/income; users can use the existing link-record workflow to reconcile actual entries with schedules. Native picker/WebView, password keyboard, backgrounding, safe areas, font scaling and assistive technology still require actual Android/iOS testing.
